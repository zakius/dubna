# Firefox WebExtensions climb

## Goal

Firefox add-ons run in oganesson and tennessine as they run in Firefox. The goal has two measures:

1. The 1000 add-ons with the most users on addons.mozilla.org (AMO) install and work. The ones that need an account wait until the others work ("Add-ons that need an account").
2. Firefox's own WebExtensions tests pass, after we port them to our test harness.

We get there in small steps (the "climb"). Each step is one API, one install flow, one behaviour or one improvement to the tools. Each step is released, so each step is useful alone.

## Where the code goes

- Shared code goes in dubna: new files in `src/` and small patches in `patches/`, as for the other shared features. Both browsers build them. The patches follow the dubna README's "Patches that last".
- Code goes in one browser only when there is a reason: UI that only that browser has (a desktop side panel, the location bar), or a patch that doesn't apply on the other browser's tree. Titanium (tennessine) patches the extensions code a lot, so check each shared patch on both trees.
- The test harness and the corpus runner are in oganesson's `tools/e2e/`, because they drive the desktop browser. The corpus list, the static scan and the score page are in dubna, because they don't depend on a browser.
- A download the browser makes by itself for Firefox add-ons (the AMO update check, the update's `.xpi`) follows browser traffic's own row for Firefox add-ons, `firefox_extensions`, apart from Chrome Web Store extensions. The bundled uBlock Origin is neither: its code ships with the browser, and its filter lists have their own row.
- Desktop comes first. Each step says what tennessine gets: now, in a later step, or never (with the reason). For now, Firefox for Android (Fenix) sets what tennessine gets: the APIs, manifest keys and behaviour that Fenix has (`firefox_android` in MDN's browser compatibility data), for the add-ons that AMO lists for Firefox for Android. tennessine installs only those add-ons. The exception is what tennessine has and Fenix doesn't: containers. tennessine gets the container APIs (`contextualIdentities`, `cookieStoreId` in `tabs` and `cookies`) and installs Multi-Account Containers. For another API that Fenix lacks, tennessine gets no test, UI or work of its own; a shared patch still has to apply on its tree. Taking more than Fenix has comes later, in steps of its own.

## Firefox add-ons only

Chrome Web Store extensions run on the same code, and many of them tell Chrome from Firefox by what they see: whether a member exists, whether a call throws, what a result holds. One that sees a Firefox behaviour takes its Firefox path, which can break it (Violentmonkey, #239). So what the climb adds or changes is a Firefox add-on's alone, and every other extension sees Chromium as it is:

- A Firefox add-on is what `IsFirefoxAddOn()` says (`src/extensions/common/firefox_add_on.h`): every add-on installed from a `.xpi`; never one from a `.crx`, even with a Gecko ID in its manifest; and an unpacked folder whose manifest has a `gecko` key.
- API schemas: what the patch adds is marked `"firefox_only": true`, and a requirement it relaxes gets Chromium's value in `"chromium"`. Other extensions' bindings read the Chromium view: the member, property, enum value or choice isn't there, a call with it throws as in Chromium, and results and events lose the marked properties (`src/extensions/renderer/bindings/firefox_schema_view.h`).
- A Firefox namespace or feature has `"requires_delegated_availability_check": true` in its `_api_features.json` entry and its name in `src/extensions/common/firefox_add_on_availability.cc`.
- Behaviour in C++ and JavaScript checks `IsFirefoxAddOn()`, or `everyone.json` says why every extension may get it: a manifest Chromium refuses loads, the browser's own fixes, plumbing for a Firefox add-on's code.

`tools/firefox_gates.py` checks all of this without a browser, in about a second: the Chromium view of each schema the patch changes is Chromium's schema exactly (`upstream/` holds Chromium's copies; run `--refresh` when Chromium moves), each feature the patch adds or widens has the check, and each code hunk names the gate, calls a function that does, or has its reason. oganesson's pre-commit hook and release workflow run it. A failure names what to mark, flag or gate.

Two browser checks back it up. oganesson's `tools/e2e/test_firefox_add_ons_only.py` runs one probe of each kind of mark in a Chrome extension, a Firefox add-on, and a `.crx` with a gecko key, among the browser tests of every build. `tools/e2e/chromium_tests.py` runs Chromium's own extension API tests (its `chrome/test/data/extensions/api_test/`, of the namespaces the climb touches) as Chrome extensions: each test that passes in stock Helium of the same Chromium, as `chromium-tests.json` lists them, has to pass in oganesson. Many of Chromium's tests need its C++ test fixture, so the list keeps only what passes in stock Helium; run `chromium_tests.py --baseline` with stock Helium when Chromium moves. The release workflow runs the full list after the ported Firefox tests, and stops on a test that fails. During a climb run, `--only` runs the tests of the namespaces a step touches; the release's full run is the check.

## The old work

The WebExtensions work from Chromium 154 is archived in `.worktrees/oganesson-webextensions` beside the main checkouts (`main/patches/core/firefox-*.patch`, `main/patches/ui/firefox-*.patch`, and the status table in `main/docs/firefox-webextensions.md`). Use it as a reference only. Don't apply it as it is. Each archived patch is a climb step: rewrite it to the current rules (new files, small hooks, no edits to an upstream's patches), on the current Chromium, with a test.

## How we measure

### Corpus score

`corpus.json` lists the top 1000 add-ons on AMO by users, without the ones in `needs-account.json` and the ones Firefox itself refuses to install, in `firefox-refuses.json`: what doesn't work in Firefox needs no work here. Each entry gives the Gecko ID, the version and the SHA-256 of the `.xpi`. The list is fixed. Refresh it once a quarter, in its own commit, so a score change never comes from a list change. A refresh brings in new add-ons: check each one, and add the ones that need an account to `needs-account.json`, and the ones Firefox refuses to `firefox-refuses.json`, before the commit. The `.xpi` files are cached outside the repo.

Each add-on gets the highest level it passes:

| Level | Check |
|---|---|
| L0 | The manifest reads as JSON. |
| L1 | The add-on installs from its `.xpi`. |
| L2 | The background starts, and no error names a missing API or manifest key. |
| L3 | A smoke check passes: the popup opens, the content scripts run. |
| L4 | A hand-written test for this add-on passes (Pouch, uBlock Origin, Dark Reader, Sidebery and others we pick). |

L1 installs each add-on's `.xpi` as a user's download does: the corpus runner serves it from a local server, a page goes to it with a user gesture, the browser installs it packed through the sandboxed unpacker, and the runner accepts the install prompt. An add-on that doesn't install, for example one with neither a Gecko ID nor AMO's signature, or with an image the browser can't decode, stays at L0 with the browser's error as its reason. Then the browser restarts, as a user's next start, and L2 and L3 run on the installed add-ons there.

The corpus runner (oganesson's `tools/e2e/corpus.py`, whose docstring says how it checks each level) writes the count for each level to `score/<browser>.json`, with the date and the browser version. It runs 8 groups of add-ons at a time, each in a browser of its own. Every oganesson release runs it in full ("Keeping what works"). The site's `firefox-add-ons.html` shows the newest counts.

### Test score

`firefox-tests.json` lists the WebExtensions test files in Firefox's source (`toolkit/components/extensions/test/` and `browser/components/extensions/test/`). Each file has one of these states:

- `ported`: it runs in our harness. The score counts how many of these pass.
- `todo`: not ported yet.
- `n/a`: it tests a Gecko internal, not WebExtensions behaviour. Each `n/a` has a one-line reason. Without this list, 100% can't be reached.

`tools/firefox_tests.py` writes the list from a sparse clone of Firefox's source, cached outside the repo. It keeps the `ported` files and an `n/a` written by hand (with `"by_hand": true`), and marks the rest by its rules again. A port is a Python file in oganesson's `tools/e2e/firefox/`, named in the file's `port`. It keeps the test's add-ons as Firefox has them, with their `browser.test` checks, and turns the test's own steps into Python (`extension_test_utils.py`, Firefox's `ExtensionTestUtils`). A port leaves out only a check of a Gecko internal, and names it in its docstring. Where Firefox sets something this browser has in another form (a pref, a container's number), the port uses this browser's form, and says so.

oganesson's `tools/e2e/firefox_tests.py` runs the ports and writes `score/oganesson-firefox-tests.json`: the date, the browser version, how many ported files pass, how many are ported, how many files aren't `n/a`, and each port's passing tests and first failure. A file passes only when all of its checks pass. The site's `firefox-add-ons.html` shows the newest counts. The release notes of a browser release that touches WebExtensions end with them too, for example "Firefox's WebExtensions tests: 3 of 843 pass (13 ported so far)": `tools/release_notes.py` adds the line from the score in the browser's dubna submodule.

Port tests together with the API they test, not all at once. The APIs that shipped before the tests existed get theirs first (the batch order). A port that fails on something not built yet is still worth having: its failures name the gaps, and each gap gets a step.

### Choosing the next step

The static scan (`tools/amo_corpus.py scan`) reads every add-on in the corpus. It lists the manifest keys and the `browser.*` calls that Chromium doesn't have, and the number of add-ons each one blocks. Among steps of the same class in the batch order ("The batch" below), the next step is the one that unblocks the most add-ons for its size. This is the hill-climb rule: within a class, the order isn't fixed in advance. Check it again after each step.

## Add-ons that need an account

An add-on that can't do its main job until the user signs in isn't in the corpus. It needs one of these:

- an account with its own service: password managers, paid VPNs, cashback, web clippers, mail checkers, time trackers;
- a security suite's subscription, or an organization's account;
- an account on the site it works on, when that site shows its content only to signed-in users: WhatsApp, Telegram, Gmail, X's timeline, streaming services, AI chats, online games.

An add-on that changes a site that is also public, such as YouTube, Twitch, Reddit or the Steam store, stays in the corpus. An add-on that needs a desktop app but no account (KeePassXC-Browser, a download manager's integration) stays too.

`needs-account.json` lists these add-ons, with what each needs: 161 of the top 1000 on 2026-11-15. Climb work for them waits:

- The static scan and the corpus runner don't read them, so the ranking and the score don't count them.
- A missing API or manifest key that only they use gets no step. A step that also unlocks account-free add-ons is ranked by those.
- When the account-free add-ons work, we check these by hand, with real accounts, and file steps for what breaks.

## Steps

Each step is a GitHub issue with the `climb` label and a size label (`size: nit`, `size: minor` or `size: medium`), in the repo where its code goes. Find them all with:

```sh
gh search issues --owner zakius --label climb --state open
```

A step body says:

- what it unlocks: which add-ons, which tests, or which later steps;
- its archive source, if it has one;
- what tennessine gets;
- `Depends on #N` for each step that must ship first;
- **Firefox's tests:** the files of `firefox-tests.json` that test what it builds, `todo` or `ported`, or "none" when no Firefox test does (UI of this browser, the tools, the corpus);
- how to check that it is done.

To find a step's tests, look up its API and its file names in the list, for example `jq -r '.tests[] | select(.api == "theme") | "\(.state) \(.path)"' webextensions/firefox-tests.json`, and read the files: a name can mislead.

A step must fit into one evening run, its Firefox tests included. It may continue into a second run, but never into a third. A step that is too large for this is split before work starts, each part with the tests of what it builds. A test file that several steps share is ported by the first of them; the others run it. Tool work counts as a step: an improvement to the harness that a later step needs soon is enough for one evening. Build only the tools that the next few steps use.

A larger goal, for example "Sidebery works", is a group of steps. Name the goal in each of its steps.

### Filing new steps

The tool steps find most of the work, so they file many new steps. That is expected. The static scan, the test inventory and each corpus run file steps for what they find:

- one step for each missing API or manifest key, even when only one add-on uses it; the batch order and the ranking set the order, not the filing;
- tests that wait for an API go into that API's step, under "Firefox's tests"; a step only for porting tests is filed when the API already works;
- a new cause of a failure in a corpus run (an error that is not yet in a step) gets its own step.

Before filing, search open and closed `climb` issues. If one already covers the item, add to it instead. Group very small items of one namespace into one step. Give each new step a size label and its `Depends on` lines.

## When a step runs

The evening task (dubna `README.md`, "Update policy") does a batch of climb steps when:

- no update was due, and
- the tracker batch was empty, or it was small enough that the climb batch can still be pushed by 06:00. The agent decides.

The 06:00 is the first one at least 4 hours after the chain begins (docs/nightly.md): a run started early in the day, by hand or on schedule, works on until then. Builds run at any hour; during the day the system gives them fewer CPUs.

Before it picks its work, each climb run checks for new Firefox tests: it runs `tools/firefox_tests.py`, which fetches Firefox's source again and names each test file that is new since the committed list ("new in Firefox's tree"). It ports every new `todo` file in that run, as "Test score" says, whatever the run does next, and commits the new list with the ports set `ported`. A new `n/a` file needs no port. The ports join the release run's full run of the ported Firefox tests, and their failing checks name gaps for steps, as any port's do. When the new files are too many for the run, it ports those of the APIs that shipped first, and files the rest as one step for porting Firefox's tests (class 2 of the batch order below), with the files under "Firefox's tests".

The climb is mostly implementation: most of a run is coding, and the build and the test runs are shared by the whole batch, so a bigger batch costs little more running. The batch is as many steps as one build can ship by 06:00: aim for four to six `size: nit` or `size: minor` steps, or one `size: medium` step with up to two small ones. With less time left, it takes fewer. The run may hand independent coding to a few helper agents (docs/nightly.md); it builds, tests and pushes the batch to main itself, with no release tag: the daily chain's release stage releases the browsers once a day (docs/nightly.md, "Releasing"). It picks the open `climb` steps whose `Depends on` steps are closed, in this order: regressions ("Keeping what works"); the install path, so that users can get Firefox add-ons at all (zakius/tennessine#47 a `.xpi` download on Android, zakius/tennessine#48 AMO's button on Android, then the other caveats of the site's `.xpi` row); the gaps that failing ported Firefox tests name, since those tests show at once whether a fix works (take steps of one API together, so they share their ports); add-ons working fully (the L4 tests of the add-ons listed under "How we measure", zakius/oganesson#71 first); then the best gain for their size by the corpus score. A step only for porting more of Firefox's tests (no API code) comes after all of these: a step still ports the `todo` tests of the API it builds, and each run still ports the files that are new in Firefox's tree. A step that another step in a higher class depends on ranks with that step. A step that starts only more add-ons (L2) never goes before one that lets users install or fully use them. It doesn't take a `blocked` step. Each step is its own commit and its own row in the status table, but the batch shares one build per browser. A step that breaks the build or the tests without a small fix is dropped from the batch, and the rest ship.

While the batch is worked on, a test run takes only what the change can affect: each step's ports and the add-ons it affects (`--only`), and after a fix, the ports or add-ons that failed and those the fix can touch. A change to the runner itself affects every add-on, so the corpus run of such a change is a full one. The full runs of the ported Firefox tests and of the corpus belong to the release: oganesson's release workflow runs all the ported tests and then the full corpus on the release build, and stops the release when a test goes `DOWN` or an add-on drops a level. The stage that tagged the release commits both scores that run wrote (`work/release-scores/`) to dubna (docs/nightly.md, "Releasing"), and the climb's next submodule move takes them, so the next release compares with them.

Long jobs don't hold up the coding. While a build or a long test run goes on, the run may hand the next steps in the order (not the batch's) to helpers, each in its own worktree from main, not from the batch, which can still change. They code and commit only, and the run waits for them, so it starts them only before a job that takes longer than their step. What they finish goes to `climb-<repo>-<issue>` branches with a comment on the issue. The next run continues those steps before new ones, building and testing them as any step; a full corpus run that is due still goes first. A helper's coding doesn't count as a run of the step.

If a step isn't pushed by about 06:00, the agent pushes the steps of the batch that are done, stops the rest, pushes each to a branch `climb-<repo>-<issue>`, and writes in the issue what is done and what is left. The next run continues it. If the second run can't finish it either, the agent pushes the part that works (if it is useful alone), files the rest as new steps, and closes the issue.

When the last full corpus run, in a release or not, is more than 7 days old, or ran on an older oganesson version than main's, the climb work for that evening is a full corpus run and a score update instead of a batch.

## Keeping what works

Each Chromium update can break a step that already shipped: a patch hunk moves, an API changes shape, MV2 loses more code. Shipped steps stay checked:

- Each step's end-to-end test stays in oganesson's `tools/e2e/`, so every update's test run covers it.
- Its ported Firefox tests stay in `tools/e2e/firefox/`, which that test run doesn't load. They run in every oganesson release (its release workflow, which stops the release on a `DOWN`), so on every update, a zero-day one too, and on the climb's pushes once a day (`firefox_tests.py`, 8 ports at a time, about 8 minutes). The stage that tagged the release commits their score (docs/nightly.md, "Releasing"). A test that passed and fails now is a regression, as a level drop is: the run prints it as `DOWN`, exits 3 (another status but 0 means the run itself failed) and keeps that port's browser profiles and logs, where the others go (`OGANESSON_E2E_KEEP=1` keeps them all). It compares with the score committed in the dubna tree it is given (`--dubna`, by default oganesson's dubna submodule), so a rerun compares with the same score. On a zero-day update, whose stage has no corpus run, the stage commits the test score alone before the tag.
- Each oganesson update that is not a zero-day runs the full corpus after its build. tennessine shares the patch, so its patch check catches a moved hunk. A zero-day update's stage skips it.
- Every oganesson release runs the full corpus after the ported Firefox tests (`corpus.py`, 8 groups at a time), so a zero-day update's release does too, and stops the release on an add-on that is a level lower than in the score committed in the dubna tree it is given (`--dubna`, by default oganesson's dubna submodule). The add-ons that went down run once more, and the better level counts: some levels vary between runs (zakius/oganesson#85). The run prints each add-on that changed level, and exits 1 on a drop after it writes the score. The stage that tagged the release commits its score with the test score (docs/nightly.md, "Releasing").
- An add-on that drops a level on an update doesn't hold the update back. If the fix is small and clear, the update stage fixes it. Otherwise it files a `climb` step for the regression ("Firefox add-ons: <what> broke on Chromium <N>"), with the add-ons it drops and the step that added the code, and records the lower score with the reason. The next climb batch takes regressions before new steps.

## Done

A step is done when:

1. It builds, and the patch check applies every patch with zero fuzz on each browser that gets the step.
2. Its Firefox tests (the body's "Firefox's tests") are ported, as "Test score" says, and the tests and checks of what the step builds pass. Port them first and run them on the build without the step, then on the build with it: `firefox_tests.py --only <ports> --dubna <the dubna worktree>`, since the list that sets them `ported` is in that worktree until it lands. The run lists each port's tests, `pass` or `FAIL`: compare the two runs' lists. Its exit status compares only with the committed score: 3 (`DOWN`) when a test that passed there fails now. A check that still fails stays in the port, with its gap in a step. What no Firefox test covers, such as this browser's own UI, gets an end-to-end test of its own. The issue's "Done when" adds to this, never replaces it.
3. The corpus run of the add-ons it affects passes at the same level or higher. The score never goes down: a drop blocks the push, unless the step explains why and files a step to fix it. A Pouch regression always blocks the push.
4. The status table below is updated.
5. It is on main: the browsers move their dubna submodule and merge to main, or (tool work) the tool or the score page is merged. The daily chain's release and site stages tag the releases (README "Releases"). The release notes give the score change, for example "L2: 612 → 640". The Firefox test score's line comes by itself ("Test score").

A step that fails twice gets the `blocked` label and a comment that says why. Then take the next step.

## Risks

- **Manifest V2.** Most top add-ons are MV2. oganesson keeps MV2 with ungoogled-chromium's `extensions-manifestv2.patch`, tennessine with Titanium's `patch.sh`. Chromium removes more MV2 code in each milestone. Check both at each milestone. If MV2 goes, the corpus score falls a lot.
- **Large APIs.** `tabs.hide`, `sessions` values and `menus.overrideContext` touch tab and menu code in each browser. `contextualIdentities` depends on the containers work (Brave-based containers in dubna).
- **Machine load.** Corpus runs use the builds lock and follow the load rules.
